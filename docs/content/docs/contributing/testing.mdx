Adding some unit tests is a great way to ensure that the bindings work as expected.
It illustrates how the bindings are supposed to be used and can help to catch regressions.

## Testing the bindings

Add a ReScript fixture under `tests/`, following the source module's directory structure. Register
each fixture in exactly one category in `tests/fixtures.json`: `compileOnly`, `nodeRuntime`, or
`browserRuntime`. `npm test` fails if a fixture is missing from the manifest or appears in multiple
categories, compiles all fixtures, and executes only the Node runtime modules. Compile-only
examples are never executed.

- src
  - DOMAPI.res
  - DOMAPI
    - HTMLCanvasElement.res
- tests
  - DOMAPI
    - Classify\_\_test.res
  - FetchAPI
    - Headers\_\_test.res

</FileTree>

Add a small sample of valid code that uses the bindings you've changed.
Add it to source control and run

```shell
git add tests
npm test
```

Run the focused checks that match your fixture:

```shell
npm test                 # compile fixtures and execute Node-compatible runtime tests
npm run test:browser     # execute native-browser regressions in Chromium
npm run test:negative    # verify expected compiler failures and diagnostics
```

Use the browser suite for APIs that require a real browser. Node's built-in Fetch support is useful
for Node runtime coverage, but is not a substitute for Chromium validation; DOM emulators are not
browser evidence either. Keep examples that need special setup, such as a GET request with a body,
compile-only unless they are deliberately configured as a runtime fixture.

## Why add tests?

Sometimes adding a test can feel like a bit of a hassle. But we insist that you add tests for the following reasons:

- **Documentation**: Tests are a form of documentation. They show how the bindings are supposed to be used.
- **Regression**: Tests help to catch regressions. If a change breaks something, the test will fail.
- **Awareness**: Tests make you aware of the API you are using.
  In the future we might trim down the generated bindings to only include the most used APIs.
  If you have a test, you can be sure that the API is not going away.
